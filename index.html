pigs 当前架构总览

当前代码事实：普通请求走前置代理透传；POST 到三种协议路径且 model 以 -pigs 结尾时，进入 Pre → Executor → Post 编排。

请求如何分流

条件当前行为
内部 loopback 请求跳过 -pigs 判断，直接进入透传通道。
POST + 已识别协议路径先解析 JSON 读取 model。JSON 非法直接返回 400；合法且 model 带 -pigs 才编排，否则使用原始 body 继续透传。
其它方法或路径直接透传。

已识别协议为 OpenAI Chat /chat/completions、Anthropic Messages /v1/messages、OpenAI Responses /responses；协议判断也接受以这些后缀结束的路径。

编排做什么

编排把一次 -pigs 请求拆成若干上游请求。模型名发上游前去掉 -pigs；每个 pig 的相位提示只在进入该 pig 时注入一次。Pre 会显式整理目标、会影响结果的关键条件和歧义/不确定性，再决定简单或复杂路径。Executor 完成后，Post 不从原始请求重建，而是直接继承 Executor 的完整协议上下文，并只在末尾追加一条评审 user 消息，以尽量保持长前缀稳定。Post 允许单独一行 PIGEND/PIGFAIL 作为路由信号，而 Pre 仍要求控制标记前已有实质文本。工具调用不会在 pigs 内执行，而是暂停当前相位，交给客户端执行；恢复时复用该 pig 的基础请求，只追加后续原生对话，不重复注入相位提示。任何 phase 若上游明确以 token 上限原因结束，则按截断错误终止，不把半截输出继续送入下一 phase。

客户端看到的编排响应由 pigs-protocol 重新合成，并不是某一次上游响应的原样转发。响应中的 model 使用客户端原始 -pigs 名称。

三个协议分别选择自己的 base，再拼接客户端原路径与 query。未识别路径使用 upstream.openai。命令行 --base-url 会临时把三个 base 全部设置成同一个值。

启动时优先读取根目录 config.local.toml，不存在时回退到 config.toml；两者都不存在才生成默认 config.toml。config.local.toml 用于本机私有覆盖并被 Git 忽略。当前生效配置的 key 留空时保留客户端鉴权头；非空时会覆盖客户端的 authorization / x-api-key，同时写入 Bearer 和 x-api-key 两种形式。

当前内部测试阶段 HTTP 抓包默认 max：每个客户端、内部 loopback、真实上游的请求/响应分别写入 logs/http，完整记录 JSON/SSE body。编排请求另外记录 orchestration-decision / orchestration-outcome，用于直接看请求为何被判成 resume、新开一轮或冲突。敏感头与常见敏感 query 参数自动打码；body 不做语义脱敏。流式响应文件还带 capture_complete，可以直接判断响应是否中途断开。

请求头与压缩

透传不是“所有 header 一个字节不改”：host、content-length、connection、transfer-encoding 会被过滤。其它端到端头默认保留。

普通 passthrough 的上游客户端关闭自动 gzip / brotli / deflate 解压，因此压缩 body 会与 content-encoding 一起回客户端。

编排子请求如果没有 content-type 会补 JSON content-type；没有 x-opencode-session 时会生成稳定的 UUID v7。loopback 还会加入随机 x-pigs-loopback。

当前已知事实：x-pigs-loopback 没有在真实上游转发前被过滤，因此当前会被带到上游。这里先如实记录，不在本轮修改代码。

usage 与响应

当前实现不做跨相位 token 求和。状态机保留 usage.input_tokens 最大的那个完整 usage 对象；工具暂停响应在 proxy 层使用 usage: None。

OpenAI Chat 常见的计数字段是 prompt_tokens，但当前比较逻辑只看 input_tokens；没有该字段时按 0 比较。这是当前代码行为，不在文档中伪装成累计策略。
