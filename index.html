pigs 新架构总览

一句话：外部请求进来，看 model 名字带不带 -pig；不带就直接转发，带了就交给编排引擎加工。 pigs 以后只做这一件事。

先用一个比喻把全局说清

把 pigs 想象成一栋楼的前台传达室：

  • 客人（客户端 Agent，比如 Claude Code）递进来一张条子（HTTP 请求），条子上写着要找的人名（model id）；
  • 前台看一眼名字：名字后面没贴 -pig 标签 → 条子原封不动送进里屋（上游 API），答复原路带回——前台一个字都不改；
  • 名字后面贴了 -pig 标签 → 交给楼里的秘书处（编排引擎），秘书处会把这一件事拆成好几步跟模型往来（先准备、再执行、后加工），最后把成品交回前台送出去。

传达室本身不打电话查号（不做模型映射）、不重拨（不做重试）、不认识具体哪家快递（上游是谁无所谓）。

一次请求的完整旅程

客户端 Agent ▼ 发 HTTP 请求（三种协议之一） pigs :3927（前台） ▼ 看 model 名字
没有 -pig有 -pig
原样转发到上游，答复原样流回 交给编排引擎：拆成 Pre → Executor → Post 多次与模型的往来；要流式就边产生边推给客户端， 最后合成一个答复（= 三只 pig 的可见文本按顺序拼接）
▼ 上游（mini-proxy 或任意直连 API）

四个 crate，各管一段

crate干什么（一句话）详细说明
pigs电源开关：解析命令行、读配置、把服务跑起来crates/pigs/index.html
pigs-proxy前台本台：接 HTTP、分流、透传、流式回传crates/pigs-proxy/index.html
pigs-orchestrator秘书处：把一个 -pig 请求拆成多次模型往来再合成crates/pigs-orchestrator/index.html
pigs-protocol字典：三种协议长什么样、怎么读怎么写crates/pigs-protocol/index.html

依赖是一条直线，永不回头：pigs → pigs-proxy → pigs-orchestrator → pigs-protocol。最底层的永远不知道最上层存在。

上游是谁？pigs 不关心

配置里只有一个 base_url。它填 mini-proxy（127.0.0.1:7946）就享受它带来的会话头、模型映射、自动重试； 填任何直连的上游 API（如 https://api.anthropic.com）也可以——三协议按路径自动区分，同一个地址。 切换上游 = 改一行配置，pigs 的代码一个字不变。

分工纪律：重试、模型映射、思考强度注入、x-opencode-session 补头——这些全都不在 pigs 里。 pigs 没接到子请求就向上抛错，绝不自己重拨。串联 mini-proxy 时由它扛，直连时由下游 Agent 自己扛。

配置只有三行

listen   = "127.0.0.1:3927"          # 我在哪监听
base_url = "http://127.0.0.1:7946"   # 往哪转发（唯一必填）
#key = ""                            # 留空 = 透传客户端的 key

为什么能这么少？因为 pigs 不按模型名路由（只看 -pig 后缀，是代码规则不是配置）， 所以旧工程里 models 列表、model_map、多供应商、兜底路由那一整层配置彻底消失。 提示词、相位定义也全是代码（include_str! 嵌入），换台机器要改的只有上面三行。

这次"大手术"切掉了什么

旧工程（已整体归档在 legacy/）里的这些器官不再保留： CLI 交互、TUI 界面、工具执行（bash/file/MCP）、会话管理、权限系统、多协议 SDK 直连（pigs-llm）、 重试与模型映射。它们属于"coding agent 产品"，而 pigs 新定位只有编排。 旧代码中值得回收的部分，在各 crate 的说明页里逐文件列了"从 legacy 收编"清单。
