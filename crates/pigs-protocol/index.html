pigs-protocol

三种协议的公共字典。全仓库最底层，谁都可以依赖它，它谁也不依赖。

为什么需要它？（ELI5）

模型世界里流行三种"电报格式"，说的其实是同一件事，但写法完全不同：

协议谁在用（例子）一句话特征
OpenAI Chat Completions大多数工具，路径 /chat/completions消息里用 "role": "assistant"，回答叫 choices
Anthropic MessagesClaude Code，路径 /v1/messages回答叫 content_block_delta，鉴权用 x-api-key
OpenAI ResponsesCodex 等，路径 /responses输入叫 input，事件叫 response.output_text

前台（proxy）收到条子要看懂才能判断 -pig；秘书处（orchestrator）要改写才能编排。 如果两边各自写一套"怎么读这三种电报"，同一段解析逻辑就会抄两份、改一处漏一处——旧工程正是踩过这个坑。 所以把"怎么读、怎么写这三种格式"抽成唯一的一本字典，大家都来查这一本。

要实现的三块内容

① 消息模型（结构体）

每种协议定义一套纯 serde 结构体：请求（messages / input / system / max_tokens / tools…）、 响应（content、tool_calls、usage…）。不带任何行为，只有数据——就像字典只给词条不给例句。 特别地，旧的 pigs-core 是围着 SDK 建的，这次彻底去掉 SDK 依赖，结构体直接对齐线上协议。

② JSON 与 SSE 编解码

JSON：请求体进、响应体出，一进一出。

SSE（流式）：模型的回答是一个字一个字蹦出来的，格式长这样：

event: content_block_delta
data: {"type":"content_block_delta","delta":{"text":"你"}}

data: {"type":"content_block_delta","delta":{"text":"好"}}

要实现一个增量解析器：喂给它不完整的字节块，它吐出"目前拼到了哪个事件、文本涨了几个字"。 透传时用它读（预读判断是否错误事件），编排时用它拼（把多次往来的文本拼成成品）。两边共用这一个实现。

③ 两条字符串规则（全仓库唯一的定义处）

  • -pig 规则：model 名以 -pig 结尾 → 走编排；剥掉后缀得到的名字才是真正发给上游的名字。 例：claude-opus-5-pig → 编排，上游实际请求 claude-opus-5。全仓库只有这里认识这个后缀，别处只调用。
  • 路径规则：请求按裸路径区分协议（/chat/completions、/v1/messages、/responses）； 转发上游时 = base_url + 协议后缀（append 约定，三协议共用一个地址）。

从 legacy 收编什么

legacy 文件拿什么
crates/pigs-api/src/protocol.rs三协议的编解码骨架
crates/pigs-api/src/phased_api_convert.rs协议之间/相位之间的转换逻辑
crates/pigs-core/src/message.rs消息模型（去 SDK 化重写为纯 serde）
crates/pigs-proxy/src/protocol.rs裸路径判定（45 行，几乎原样搬）

红线

  • 不做 HTTP：没有 axum、没有 reqwest——它只是字典，不打电话；
  • 不做重试、鉴权决策、模型映射（这些概念在本仓库已整体移除）；
  • 不认识 -pig 之外的任何模型名语义。
验收标准：给它一段真实抓包的请求/响应字节（三种协议各来一套、流式非流式都有）， 它能解析成结构体再原样序列化回去，字节级等价。做到这个，上层两个 crate 就能放心依赖它。
