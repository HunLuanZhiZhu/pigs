pigs-proxy

当前实现：一个 axum fallback 接住所有方法和路径，负责分流、上游转发、loopback 以及把编排结果编码给客户端。

入口分流

输入当前处理
带合法 x-pigs-loopback 的内部请求跳过编排判断，直接走 passthrough，避免递归。
POST + 三协议路径先尝试解析 JSON。非法 JSON 返回 400；合法后读取 model，带 -pigs 或 -pig 则编排，不带则继续透传原始 body。
其它请求直接 passthrough。
Pre 内容的路由：proxy 负责剥掉后缀并传入真实模型名，orchestrator 再按名称包含 deepseek / muse 选择分别的历史 v5 / v6 完整模板；均未命中时使用通用 Pre。普通透传请求完全不执行 Pre。

上游地址

配置不是单一 base_url，而是三个协议 base：upstream.openai、upstream.responses、upstream.anthropic。未识别路径落到 OpenAI base。

上游 URL 的计算是“按协议选 base + 客户端原路径 + 原 query”。不会把客户端路径替换成固定协议后缀。

请求头

Upstream::forward_headers 会过滤 host、content-length、connection、transfer-encoding。其它端到端头默认保留。

配置文件由 pigs CLI 选择（config.local.toml 优先于 config.toml）。当当前生效配置的 key 非空时，客户端的 authorization 与 x-api-key 会被移除，再写入：

  • authorization: Bearer <key>
  • x-api-key: <key>

因此“所有请求头原样透传”不是当前实现。

普通 passthrough 与压缩

passthrough 保留上游状态码并把响应 body 作为字节流回传。响应头跳过 connection、transfer-encoding、content-length，但保留 content-encoding。

面向真实上游的 reqwest 客户端显式关闭 gzip / brotli / deflate 自动解压，目的是让压缩 body 与编码头保持一致。

-pigs / -pig 编排

proxy 解析 model 后缀：-pigs 选择模式 A，-pig 选择模式 B；随后去掉后缀写入真实上游 model，并把模式放入 TurnInput。客户端是否流式由原 body 的 stream 布尔值决定。

编排配置从当前生效的 [orchestration] 读取：max_executor_runs 默认 4，max_post_protocol_retries 默认 3，usage_mode 默认 max。usage_mode = "max" 返回总 token 最大的一次真实调用 usage；sum 对本次客户端请求触发的真实调用 usage 数值字段逐项求和。A/B 共用同一组配置。

proxy 会扫描当前请求中的全部工具结果 id，并从 ContinuationStore 中寻找其 pending id 已全部出现的现场；匹配成功后先 claim 并标记 in-flight，再恢复同一只 pig，不要求工具结果处于请求绝对尾部。resume 成功后才 commit 删除旧 continuation；resume 失败则 rollback 保留旧现场，客户端可以重发同一批工具结果。若匹配现场正在被另一个请求恢复则返回 409 提示稍后重试；若确实找不到现场也返回 409。每次 Paused 响应只返回当前这轮新产生的工具调用，已消费的历史 ToolCall 不会跟着 continuation 进入下一次响应。

非流式编排完成后调用 synthesize_json；流式请求则立即返回 SSE body，后台运行状态机并通过 StreamEncoder 持续发帧。最终收尾由编码器自行关闭仍打开的块后再发送终止事件，避免 Responses 的 response.completed 出现空 output。

模式 A 会把普通文本增量实时交给 StreamEncoder。模式 B 会抑制阶段 ordinary-text delta，直到 Simple 的 Pre 或 Complex 的 Executor 被正式接受后，才在收尾阶段把最终业务正文写入 SSE；thinking/reasoning 和工具调用仍按原协议发送。

loopback

编排子请求不是直接从 orchestrator 发真实上游，而是由 LoopbackTransport POST 回本服务，再复用 passthrough 通道。

loopback 请求会额外加随机 x-pigs-loopback。本机 handler 只用它判断“这是内部请求”。

当前实现细节：真实上游转发时的 header 过滤列表不包含 x-pigs-loopback，所以该内部头目前会继续被发送到上游。旧文档中“上游前删除、不泄露”的说法与代码不一致。

loopback 使用默认 reqwest 客户端读取本机 proxy 返回，因此可以自动解压本机返回的压缩响应，供编排层解析 JSON/SSE。

编排响应

编排路径不会把最后一个上游响应直接交给客户端。proxy 构造 ResponseContent，其中 model 使用客户端原始 PIGS 名称（包括 -pigs / -pig），再由 protocol 层生成新的 JSON/SSE 协议壳。

Completed 与 Paused 都返回本次客户端 API 请求按 usage_mode 聚合后的 usage。工具结果回填并恢复 continuation 时，新一发客户端请求从零重新统计 usage。停止原因使用状态机记录的最后一轮值。模式 A 的 Completed parts 保留各阶段普通文本；模式 B 的 Completed parts 只加入最终 committed business text，同时继续保留已解析的 reasoning/native 非文本块。已经执行完成的历史 ToolCall 不会重放。PIGEND/PIGNEXT/PIGFAIL 都不会成为客户端业务正文。

HTTP 诊断抓包

proxy 内置独立于 tracing 的请求/响应抓包。[logging].detail 支持 off / basic / max，当前内部测试默认 max；目录由 [logging].directory 指定，默认 logs/http。

同一次 handler 交换使用相同 exchange id，并分别生成 client-request / client-response、loopback 的 internal-request / internal-response、以及 upstream-request / upstream-response 文件。编排请求还会额外生成 orchestration-decision 和 orchestration-outcome。前者记录全部/尾部工具结果 id、当时所有 pending continuation、实际匹配的 pending id 及最终路由判定；其中尾部集合只用于解释 reminder 等客户端包装，不再作为恢复条件。后者记录完成或暂停、continuation id 与工具调用 id。编排子请求经过 loopback，因此真实上游请求体（含相位 prompt）也会单独落盘。

流式响应会捕获完整 SSE；读到正常 EOF 时文件标记 capture_complete: true，若客户端连接导致响应 body 中途被丢弃则标记 false。压缩响应仅在日志副本中尝试 gzip / deflate / brotli 解压，不改变网络转发。

敏感数据：authorization、API key、cookie 和内部 loopback token 等头会自动打码，常见敏感 query 参数也会打码；但 max 模式不会改写 body，因此 prompt、工具结果、模型输出仍会以明文保存在本机。

错误状态

非法协议 JSON 返回 400；工具结果找不到 continuation 返回 409；真正以 Error::Budget 结束的非流式编排返回 422；其它非流式编排错误（包括 orchestrator 识别出的 token 截断）通常返回 502。任务执行次数统一由 orchestrator 按 Executor 高层执行次数控制；达到上限时最后一次 Executor 直接完成，不再进入 Post，因此不会因为最后一个 Post 再次拒绝而产生预算 422。Post 无控制标记的协议重试超限仍可能返回 422。流式响应一旦已经开始，后续错误只能编码在 SSE 流内。
