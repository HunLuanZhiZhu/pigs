pigs-orchestrator

秘书处：把一个 -pig 请求拆成多次与模型的往来，最后合成一个答复。本项目的灵魂。

它在干嘛？（ELI5）

普通请求是"一问一答"。带 -pig 的请求，客人要的不是一问一答，而是一道工序： 先替我把材料理一遍，再正式干，干完再按格式收拾好。秘书处就是干这个的—— 它把一件事拆成三步，每一步都跟模型打个来回，最后把结果拼成一份答复交回前台。 它自己不认识任何模型厂商：所有"跟模型打交道"都通过写好的子请求单子，交前台（proxy）去发。

三相位管线

① Pre（备料）在正式问题之前，先让模型/规则做一次准备：理清输入、补上下文、生成执行提示
② Executor（执行）正式干活：带着 Pre 的产物，把剥掉 -pig 后的原始请求发给模型，拿到正式回答
③ Post（收拾）把执行结果按约定格式加工/校验/补注，合成最终答复

每个相位 = 组装一个协议原生的子请求 + 处理它的响应。相位是固定骨架，提示词是模板（include_str! 嵌入，语言各一份），相位里模型看到什么、输出怎么用，全部由代码 + 模板决定，不进配置文件。

最终答复 = 三只 pig 的可见文本按顺序用空行拼接（Pre 的分析 + Executor 的执行 + Post 的评审），不是只取最后一只。 简单问题（Pre 直接判断并作答、末尾带 PIGEND）则整轮只有 Pre 一段。这是 legacy HTTP 运行时（pigs-api/src/http_runtime.rs）的语义，照搬。

状态机：控制标记 + 预算

相位靠模型输出最后一行的控制标记来路由（标记必须单独成行，且前面得有实质内容，防止模型光吐一个标记）：

当前相位输出末行下一步
PrePIGEND整轮结束（简单路径，只此一段文本）
PrePIGFAIL记录失败路径 → 回 Pre 重规划（预算 2 次）
Pre无标记把分析作为 {pre_output} 注入 → Executor
Executor（不解析）总是进 Post 验收
PostPIGEND整轮结束（正常路径）
PostPIGFAIL清空产物 → 回 Pre 重规划（预算 2 次）
Post无标记提示词要求它"继续执行任务" → 再走一次 Post（预算 3 次）

预算耗尽 = 本轮失败：直接报错上抛（proxy 返回 422），绝不假装成功、不拿半成品当答复。 重规划预算与 Post 重试预算都是代码里的常量（编排语义的一部分，不进配置）。

注：实现以 legacy 实际在跑的 pigs-api/src/orchestration.rs + http_runtime.rs 为准 （另一个较老的 phased_runtime.rs 是 Post↔Executor 回环、预算耗尽返回文本，那是 agent CLI 时代的形态，没有采用）。

工具调用：一只 pig 可以来回好几次

一只 pig 是一段对话区间，不是一次请求。它结束的条件是"模型这一轮不再要工具"：

模型：我要调用 Bash      → 相位暂停，调用原样交给客户端（原生 tool_calls / tool_use / function_call）
客户端：执行 Bash         → 结果写进它自己的历史，再发一发请求
pigs：按 tool_call id 匹配到现场 → 接着同一只 pig 继续 → 模型：还要再看一眼文件
  …（如此往复任意次）…
模型：不再要工具，给出这一相的产出 → 这才做 PIGEND/PIGFAIL 路由

跨这段等待的现场（相位、产物、失败路径、预算计数、已产生的可见文本、usage）存在内存 ContinuationStore 里（容量 64 / TTL 30 分钟，按 id 匹配取出即独占）。 客户端不需要知道 continuation 的存在：它照常把工具结果接回自己的历史再发请求即可。

尾部带工具结果却匹配不到现场（服务重启过、现场过期）→ 明确返回 409，不悄悄重跑一整轮。

流式：边到边拼接（动态）

客户端带 stream:true 时，子请求也带 stream:true——上游的增量一个字一个字到达，编排层边收边处理：

上游 SSE 增量 ──▶ MarkerFilter ──▶ 安全可见文本 ──▶ 客户端 SSE 帧
                     ▲
                     └─ 只压住两种尾巴：可能正在长成标记的最后一行（"PIG" → "PIGEND"，
                        连它前面的换行一起留着），以及悬在末尾还没等到下一行内容的换行。
                        其余文本一拿到就放行 —— 逐字流式，不是攒够一整行才动。

这套 MarkerFilter 的安全性来自"凡是还能拼成控制标记的部分都被压住"：已经发出去的字符， 事后不可能再与后面的字符拼成标记，所以标记绝不会漏给客户端。相位之间由 SSE 编码器补一个空行。 编排跑完时，客户端实时收到的内容与"最终答复"逐字一致（测试里就是这么对比的）。

注：legacy 的 MarkerLineBuffer 是"整行放行"——某只 pig 只输出一行时， 这行要等到流结束才吐出去（简单问题看起来就像没流式）。这里改成只延迟"可能成标记"的尾巴， 输出内容完全一致，只是更早到达；各种切片方式（含标记被切成任意片段）都有测试盯着。

客户端没要流式时，子请求也不流式：一次性拿 JSON 全文、解析文本、最后合成一个 JSON 响应——两条路径共用同一套标记判定与拼接逻辑。

为什么子请求要去掉 accept-encoding：客户端可能带 gzip，原样转给上游后回来的就是压缩体， 编排层按 JSON / SSE 解析会直接失败（真实踩过：expected value at line 1 column 1）。子请求一律不带该头，强制上游回明文。

一次编排的生命周期

客户端：model = "claude-opus-5-pig" ▼ 1. proxy 交进来（已剥后缀 → 真名 claude-opus-5） orchestrator 生成会话 ID（或继承客户端自带值） ▼ 2. Pre：组装子请求①（提示词模板 + 原始消息） loopback → proxy 透传通道 → 上游 ▼ 3. 拿到响应①，喂给 Executor 的组装 子请求② → 上游 → 响应② ▼ 4. Post：按模板加工，合成最终答复 交回 proxy → 客户端

每一步的产物都不是"只给下一步看"：Pre 的分析、Executor 的执行、Post 的评审会按顺序拼成一份答复， 客户端要流式的话，这些文本在产生的当下就推过去了（见下面的"流式：边到边拼接"）。

四个关键设计

① 会话头贯穿（prompt cache 不断）

一次编排会向上游发 好几个请求。如果每个请求的会话标识不一致，上游的 prompt cache 亲和就断了（每个子请求都被当新会话）。 所以：编排开始时生成一个稳定的 x-opencode-session（或客户端已带就继承），塞进本次编排的每一个子请求。 下游的 mini-proxy 看到客户端（这里就是 pigs）已经带了会话头，就原样透传不覆盖——两边的设计正好咬合。

② loopback 回环（不另造 HTTP 轮子）

子请求不从 orchestrator 直接发往上游，而是回环到本机 proxy 的透传通道再出去。好处：头的处理、流式转发、 错误返回这些"搬运"细节只写一份；坏处是要防递归——回环请求带随机内部令牌，handler 验证令牌后跳过 -pig 分流， 发往上游前删掉令牌。监听非回环地址时要把回环目标换算成可连地址（legacy 已有实现，照搬）。

③ 对失败的态度：不重试，如实上抛

任何子请求失败（连接不上、上游报错），编排立刻停止，把错误如实交回 proxy 返回客户端。 绝不自动重拨——重试是传输层的事（mini-proxy 或下游 Agent），编排层重试不仅职责越界， 还会在相位之间造成状态不一致（Pre 成功了、Executor 重试五次，成本和语义都乱）。

④ 纯函数化：不认识 axum

orchestrator 的公开接口大致是"给一个协议请求，还你一个可迭代执行的编排计划"。 它不依赖 HTTP 框架（没有 axum/tower），网络交互全部通过一个窄接口（发子请求、收响应）注入。 这样整条编排管线可以拿固定输入做离线单元测试，不用起服务器。

红线

  • 不做工具执行：没有 bash/file/MCP——编排只通过协议消息与模型交互（这是本次手术砍掉 agent 循环的核心）；
  • 工具调用：暂停交棒，不自己执行——tools 原样透传给上游；模型要工具时，相位暂停， 调用原样交给客户端执行；客户端带工具结果回来时按 tool_call id 匹配到现场，接着同一只 pig 继续 （见下节"工具调用：一只 pig 可以来回好几次"）。
  • 不做重试（见③）；
  • 不知道上游是谁：mini-proxy 还是直连 API，与它无关；
  • 不认识 axum：HTTP 只通过窄接口注入；
  • 不读配置文件：提示词、相位定义都是代码与嵌入模板，部署参数不经过它。

从 legacy 收编什么

legacy 文件拿什么
crates/pigs-api/src/orchestration.rs状态机本体（标记路由、重规划/Post 重试预算、预算耗尽即失败）——逐条对齐
crates/pigs-api/src/http_runtime.rsMarkerLineBuffer（流式增量去标记，本项目改为"只延迟可能成标记的尾巴"）与相位循环骨架
crates/pigs-api/src/protocol.rs相位间的 body 手术：指令追加在 user 文本后（\n\n---\n\n 分隔）、产物作为 assistant 消息接回、Post 追加新的 user 消息
crates/pigs-api/src/output.rsStreamingEncoder（客户端 SSE 帧序列：三协议各自的块开/关/终止帧）
crates/pigs-prompts/prompts/*.txtPre/Executor/Post 模板原文（中英双语，逐字节相同），改由 include_str! 嵌入
crates/pigs-proxy/src/loopback.rs回环传输与内部令牌机制

三只 pig 怎么看见彼此的产物（与 legacy 完全一致）： Pre 的分析填进 Executor 指令模板的 {pre_output}；Executor 的草稿和历次评审报告则作为 assistant 消息接回对话，Post 的验收指令是新追加的一条 user 消息—— 模型看到的是"我自己刚写的稿子请验收"，而不是"用户塞来的一段材料"。用户原话（含图片等非文本内容）全程不被覆盖。

多段产物会合成一条 assistant 消息（用空行连接）：Post 重试/重规划时草稿与历次评审会挨在一起， 而 Bedrock / Vertex 这类网关对"连续两条 assistant"直接 400（roles must alternate…；直连 A 社官方 API 则自己会合并）。 正常路径只有 Executor 一段草稿，产物本来就只有一条，发出去的东西与 legacy 逐字节相同。

验收标准：给一个固定的 -pig 请求 + 一个"假装上游"的固定响应序列， 编排输出的子请求序列（顺序、model 名、注入的提示词、会话头、stream 标志）与预期逐字节一致； 上游中途报错时编排立刻上抛、不发后续相位；流式路径下，客户端收到的 SSE 回读出的文本必须与最终答复完全相同、且不含任何控制标记。
