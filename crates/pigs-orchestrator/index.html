pigs-orchestrator

当前实现：维护 Pre → Executor → Post 状态机，把父请求克隆成多个协议原生子请求，并处理工具暂停/恢复、相位文本、usage 和停止原因。

状态机

相位模型输出下一步
Pre末尾控制标记 PIGEND简单路径完成，不进入 Executor/Post。
PrePIGFAIL记录失败路径并重新 Pre；重规划预算常量为 2。
Pre无控制标记保存为 pre_output，进入 Executor。
Executor任意正常输出不按 PIG 标记路由，产物加入 transcript，进入 Post。
PostPIGEND正常完成。
PostPIGFAIL记录失败路径，回 Pre 重规划。
Post无控制标记产物加入 transcript，继续 Post；Post 迭代预算常量为 3。

预算耗尽返回 Error::Budget。非流式 proxy 会把这种错误映射为 HTTP 422。

子请求如何组装

orchestrator 为每个 pig 建立一次基础请求，而不是每次工具恢复都重新解释客户端整段请求。

组装顺序是：

  1. 进入新 pig 时，从本轮最初的请求 body 构造基础请求；
  2. 只在这一步注入一次相位提示词：Pre/Executor 追加到当前任务 user 文本，Post 追加此前产物与一次 Post user 指令；
  3. 同一 pig 内若发生工具调用，模型的原生 assistant/tool-call 记录保存在 phase_transcript；客户端回填的尾部工具结果也追加到这里；
  4. 恢复时复用同一个基础请求，再把 phase_transcript 接在后面，不新增相位 user 指令；
  5. 序列化 JSON，形成 SubRequest。

因此一个 pig 内无论暂停/恢复多少次，相位提示始终只有一份；工具结果保持在对话尾部，模型继续刚才的工作，而不是被重新布置整阶段任务。

模型名与其它 body 字段

去掉 -pigs 的 model 修改发生在 proxy 进入 orchestrator 之前。orchestrator 本身不会调用 set_stream 或 strip_tools；客户端原有的 stream、tools、tool_choice、thinking/reasoning 等字段随克隆 body 保留。

由于 body 经过 serde_json::Value 解析再序列化，只能承诺 JSON 语义字段保留，不能承诺原始字节、空白或对象键顺序完全一致。

工具调用与 continuation

一只 pig 可以包含多轮工具往返。模型输出只要还有工具调用，当前相位就不会做 PIGEND/PIGFAIL 路由，而是先暂停：

模型请求工具
  ↓
保存 TurnState + pending tool ids
  ↓
返回 Paused，客户端执行工具
  ↓
客户端把 tool result 放回历史再次请求
  ↓
proxy 匹配 ContinuationStore
  ↓
resume 同一相位

ContinuationStore 当前默认容量 64，TTL 30 分钟，纯内存保存。匹配规则是某个 continuation 的全部 pending id 都出现在请求尾部工具结果 id 集合中；匹配后即从 store 取出，避免重复恢复。

ToolCall 是一次性的暂停信号：Paused 响应只携带本轮新产生的调用；continuation 中的最终输出 TurnState.parts 不保存这些 ToolCall。与此同时，当前 pig 的原生 assistant/tool-call 记录会进入内部 phase_transcript，用于下一轮上游对话续接。客户端回填结果后，只把新的尾部工具结果追加到该 transcript；后续 Paused 和最终 Completed 都不会向客户端重放已经消费的历史调用。

会话头与 content-type

状态机为一轮编排持有稳定的 session：若客户端已有 x-opencode-session 则继承，否则生成 UUID v7。

每个子请求发送前，如果 headers 中没有 content-type，会补 application/json；如果没有 x-opencode-session，会补当前 session。

当前不会删除 accept-encoding。旧 HTML 中“编排子请求一律去掉 accept-encoding”的说明已经过时。压缩响应由 proxy loopback 链路中的默认 reqwest 客户端负责自动解压后再交给 JSON/SSE 解析。

loopback 传输

orchestrator 只依赖抽象 Transport，不依赖 axum。实际服务中注入的是 proxy 里的 LoopbackTransport：它把 SubRequest POST 回本机 proxy，再由 passthrough 通道发向真实上游。

loopback 内部令牌 x-pigs-loopback 是 proxy transport 加的。当前 upstream header 过滤未删除它，所以它目前会继续到真实上游；这里记录的是现状，不代表目标设计。

流式

当父请求 body 的 stream 为 true 时，orchestrator 使用 transport 的 streaming 路径。上游 SSE 被增量解析并通过 ProgressSink 产生事件。

  • 文本增量经过 MarkerFilter，只抑制可能形成尾部控制标记的字符，避免 PIGEND/PIGFAIL 泄出；
  • thinking、reasoning summary、signature 等使用带类型事件传给 proxy 的 StreamEncoder；
  • 一轮结束时，无法实时还原的原生块由收尾逻辑补发。

非流式时则整轮读取上游 JSON/SSE 输出，解析成统一的 ModelOutput。

最终内容与 usage

TurnState 会把各轮去除控制标记后的可见文本按顺序保留；最终 TurnResult.text 用两个换行连接这些片段。parts 同时保存文本和解析出的非文本块，供 protocol 层合成最终响应。

stop_reason 每一轮都会覆盖，最终保留最后一轮解析到的值。

usage 不累计。当前实现比较 usage.input_tokens，保留该值最大的那一轮完整 usage 对象；平局保留旧对象。OpenAI Chat 若只提供 prompt_tokens 而没有 input_tokens，比较值按 0 处理。

工具暂停时，状态现场本身仍包含已记录的 usage；但 proxy 的 Paused 响应明确使用 usage: None，所以客户端不会收到“截至暂停点的累计 usage”。

错误处理

transport 或解析错误会立即终止当前编排，不在 orchestrator 内自动重试。是否采用额外重试策略属于其它层的职责。
