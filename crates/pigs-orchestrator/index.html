pigs-orchestrator

当前实现：维护 Pre → Executor → Post 状态机，把父请求克隆成多个协议原生子请求，并处理工具暂停/恢复、相位文本、usage 和停止原因。

调试提示：orchestrator 本身仍通过事件/状态工作；每一轮实际发出的 phase 请求与上游响应由 proxy 的 HTTP 诊断抓包记录。max 模式下可直接查看 loopback / upstream 明文文件确认相位 prompt、工具调用与 reasoning 的真实协议形状。

状态机

相位模型输出下一步
Pre实质正文后的末尾 PIGEND简单路径完成，不进入 Executor/Post；只有控制标记而没有正文仍无效。
PrePIGFAIL记录失败路径并重新 Pre；重规划预算常量为 2。
Pre无控制标记保存为 pre_output，进入 Executor。
Executor任意正常输出不按 PIG 标记路由；完整物化 Executor 会话现场，并在末尾追加 Post 的 user 指令后进入 Post。
PostPIGEND（可单独一行）接受当前 Executor 结果并正常完成。
PostPIGNEXT当前结果可修补：砍回最近一次 Executor 完成时的 checkpoint，丢弃 Post 指令与 Post transcript，再用原 Executor 指令模板把 Post 反馈作为新的执行前分析；连续修补预算为 3。
PostPIGFAIL记录根本问题，回 Pre 重规划；不表示回滚外部状态。
Post无控制标记视为核验协议未完成，继续在同一 Post 对话现场重试；无标记重试预算为 3。

Pre 使用严格标记检测，Post 使用只看最后非空行的终止标记检测。Post 只负责核验和路由，不自行执行修补；需要修补时用 PIGNEXT 把控制权交回 Executor。任何相位若 stop_reason 明确表示 token 上限截断（length / max_tokens / max_output_tokens），会返回 Error::OutputTruncated，不会把半截文本继续交给下一相位。预算耗尽返回 Error::Budget；非流式 proxy 会把预算错误映射为 HTTP 422，其它编排错误通常为 502。

子请求如何组装

orchestrator 为每个 pig 建立一次基础请求，而不是每次工具恢复都重新解释客户端整段请求。

组装顺序是：

  1. Pre / Executor 进入时，从本轮最初的请求 body 构造基础请求；
  2. Pre / Executor 只在这一步把相位提示追加到当前任务 user 文本；
  3. Executor 完成时，先把 Executor 的基础请求与完整 phase_transcript 物化成一个 checkpoint；该 checkpoint 恰好截止到 Executor 最终 assistant 输出，尚未包含任何 Post 指令；Post 请求只是在这个 checkpoint 后追加一条 Post user 指令；
  4. Post 返回 PIGNEXT 时，系统回到上述 checkpoint，丢弃 Post user 指令及整个 Post transcript；随后新增一条 user 消息，内容直接复用普通 executor_instruction 模板，只把其中的执行前分析替换为 Post 去除控制标记后的反馈；
  5. 工具 continuation 恢复除了要求 pending tool-call id 全部匹配，还要求 A/B 模式一致，避免两种输出模式互相消费现场；
  6. 同一 pig 内若发生工具调用，模型的原生 assistant/tool-call 记录保存在 phase_transcript；客户端回填时，用 pending id 定位本次恢复起点，然后把从匹配工具结果开始的客户端新增消息原样接回，包括后续 reminder / 普通 user 消息；
  7. 恢复时复用同一个基础请求，再把 phase_transcript 接在后面，不新增相位 user 指令；
  8. 序列化 JSON，形成 SubRequest。

因此一个 pig 内无论暂停/恢复多少次，相位提示始终只有一份；工具结果保持在对话尾部，模型继续刚才的工作，而不是被重新布置整阶段任务。

模型名与其它 body 字段

去掉 -pigs / -pigsb 的 model 修改发生在 proxy 进入 orchestrator 之前；proxy 同时把 A/B 模式写入 TurnInput。orchestrator 本身不会调用 set_stream 或 strip_tools；客户端原有的 stream、tools、tool_choice、thinking/reasoning 等字段随克隆 body 保留。

由于 body 经过 serde_json::Value 解析再序列化，只能承诺 JSON 语义字段保留，不能承诺原始字节、空白或对象键顺序完全一致。

工具调用与 continuation

一只 pig 可以包含多轮工具往返。模型输出只要还有工具调用，当前相位就不会做 PIGEND/PIGNEXT/PIGFAIL 路由，而是先暂停：

模型请求工具
  ↓
保存 TurnState + pending tool ids
  ↓
返回 Paused，客户端执行工具
  ↓
客户端把 tool result 放回历史再次请求
  ↓
proxy 匹配 ContinuationStore
  ↓
resume 同一相位

ContinuationStore 当前默认容量 64，TTL 30 分钟，纯内存保存。匹配规则是某个 continuation 的全部 pending id 都出现在当前请求的工具结果集合中；不要求这些结果位于请求绝对尾部。若长历史同时命中多条遗留现场，优先取最新一条；匹配后即从 store 取出，避免重复恢复。

ToolCall 是一次性的暂停信号：Paused 响应只携带本轮新产生的调用；continuation 中的最终输出 TurnState.parts 不保存这些 ToolCall。与此同时，当前 pig 的原生 assistant/tool-call 记录会进入内部 phase_transcript，用于下一轮上游对话续接。客户端回填时，pending id 只用于确认 continuation 与定位本次新增历史的起点；从匹配工具结果开始的后续客户端消息原样追加。后续 Paused 和最终 Completed 都不会向客户端重放已经消费的历史调用。

会话头与 content-type

状态机为一轮编排持有稳定的 session：若客户端已有 x-opencode-session 则继承，否则生成 UUID v7。

每个子请求发送前，如果 headers 中没有 content-type，会补 application/json；如果没有 x-opencode-session，会补当前 session。

当前不会删除 accept-encoding。旧 HTML 中“编排子请求一律去掉 accept-encoding”的说明已经过时。压缩响应由 proxy loopback 链路中的默认 reqwest 客户端负责自动解压后再交给 JSON/SSE 解析。

loopback 传输

orchestrator 只依赖抽象 Transport，不依赖 axum。实际服务中注入的是 proxy 里的 LoopbackTransport：它把 SubRequest POST 回本机 proxy，再由 passthrough 通道发向真实上游。

loopback 内部令牌 x-pigs-loopback 是 proxy transport 加的。当前 upstream header 过滤未删除它，所以它目前会继续到真实上游；这里记录的是现状，不代表目标设计。

模式 A / B 与流式

当父请求 body 的 stream 为 true 时，orchestrator 使用 transport 的 streaming 路径。上游 SSE 被增量解析并通过 ProgressSink 产生事件。

  • 模式 A（-pigs）的文本增量经过 MarkerFilter 后实时发送；
  • 模式 B（-pigsb）的普通文本在 Pre/Executor/Post 生成时不发送。Simple Path 只有 Pre PIGEND 后提交 Pre 答案；复杂路径把 Executor 普通文本先存为 candidate，只有随后 Post PIGEND 才提交；PIGNEXT/PIGFAIL 会丢弃当前 candidate；
  • thinking、reasoning summary、signature 等使用带类型事件传给 proxy 的 StreamEncoder；
  • 一轮结束时，无法实时还原的原生块由收尾逻辑补发。

非流式时则整轮读取上游 JSON/SSE 输出，解析成统一的 ModelOutput。

最终内容与 usage

模式 A 中，TurnState 继续按执行顺序保留各阶段普通文本。模式 B 中，Pre/Post 普通文本不进入客户端业务正文；candidate_text 保存当前 Executor 候选，committed_text 只保存最终被接受的业务正文。thinking/reasoning 与工具调用不受正文隐藏规则影响。流式 B 因此只延迟普通业务正文；reasoning 与工具事件仍可实时发生。

stop_reason 每一轮都会覆盖，最终保留最后一轮解析到的值。

usage 不累计。当前实现比较 usage.input_tokens，保留该值最大的那一轮完整 usage 对象；平局保留旧对象。OpenAI Chat 若只提供 prompt_tokens 而没有 input_tokens，比较值按 0 处理。

工具暂停时，状态现场本身仍包含已记录的 usage；但 proxy 的 Paused 响应明确使用 usage: None，所以客户端不会收到“截至暂停点的累计 usage”。

错误处理

transport、解析错误或明确的 token 截断会立即终止当前编排，不在 orchestrator 内自动重试。token 截断使用独立的 OutputTruncated 错误，不再与“无文本”混为一类；是否采用额外恢复/重试策略属于其它层的职责。
